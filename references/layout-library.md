# Layout library

Select the layout from the management question. Use one primary layout per slide.

| Management question | Layout | Structure | Limit |
|---|---|---|---|
| What has been achieved? | Performance dashboard | 4–5 metrics + 3–4 result blocks | 5 metrics, 4 blocks |
| Why should leadership believe it? | Evidence matrix | Metric ribbon + 2×2 evidence grid | 4 claims |
| What is wrong and why? | Diagnosis tree | Result → causes → evidence → implication | 3 root causes |
| What will we do and when? | Roadmap | Three phases or six-month table + gates | 3 phases, 6 months |
| How will the organization operate? | Capability loop | Two zones + connected roles + feedback | 6 roles |
| Which projects get resources? | Portfolio table | Initiatives × value × urgency × decision | 8 projects |
| Which option should we choose? | Comparison matrix | Options × decision criteria | 3 options |
| What must leadership decide? | Decision page | Recommendation + reasons + risk + ask | 3 reasons |
| What exactly is this project? | Project charter | Metric ribbon + background/objective/scope/success | 4 blocks |
| Is the project under control? | Project health | RAG ribbon + progress/variance/next milestone/attention | 5 statuses, 4 blocks |
| When do milestones land? | Milestone Gantt | Workstream + owner + period grid + status bars | 8 rows, 12 periods |
| Which management items need closure? | RAID table | Type + item + impact + action + owner + due + status | 8 rows |
| How does the business need trace to technology? | Solution flow | Business problem → process → data → system/AI → value | 4–6 stages |

## Performance dashboard

Use a conclusion-led title, a 4–5-cell metric ribbon, and 3–4 result blocks. Each block needs one outcome, one piece of evidence, and one implication. Avoid unrelated KPI tiles.

## Evidence matrix

Use a metric ribbon and a 2×2 card grid. Each card contains a claim, requirement or context, direct evidence, and a compressed proof band. Read [evidence-matrix.md](evidence-matrix.md).

## Diagnosis tree

Use `observed result → 2–3 root causes → evidence → management implication`. Separate symptoms from causes.

## Roadmap

Use either `validate → scale → institutionalize` or a month-by-month delivery table. Every phase needs a target, key work, deliverable, and decision gate. Do not add paragraphs below the roadmap.

## Capability loop

Use two zones and five or six roles connected left-to-right. Add one feedback line from operations back to the business or source. Read [capability-loop.md](capability-loop.md).

## Portfolio table

Recommended columns: `workstream | initiative | timing | status | value/result | decision`. Use merged category cells, one status color per row, and no explanatory footnotes.

## Comparison matrix

Put criteria in rows and options in columns. Highlight only the recommended option and decisive criteria. Replace unexplained checkmarks with short evidence.

## Decision page

State the recommendation in the title. Use three equal reason blocks. End with a compact decision strip naming the owner, resource, or approval needed.

## Project charter

Use the page as the project's one-page contract. Keep exactly four blocks: background, objective, scope, and success criteria. Put duration, team, first-release scope, and target outcome in the metric ribbon. Never mix detailed status reporting into this page.

## Project health

Use five management dimensions at most: scope, schedule, cost, quality, and risk. Each status must include a short reason. The four evidence blocks should explain completion, variance, next milestone, and the specific management attention required.

## Milestone Gantt

Show named workstreams, one accountable owner, explicit start/end periods, and a status inside each bar. Use a compact table grid and straight bars. Reserve the conclusion strip for the critical path and final date.

## RAID table

Use only real management categories: risk, assumption, issue, decision, and action. Every row requires an impact, closure action or decision, owner, due point, and current status. Keep row text short enough for one or two lines.

## Solution flow

Trace one end-to-end logic chain: business problem → process change → data/knowledge preparation → system and AI capability → measurable business value. Use square columns and straight connectors; never present the technology layer without upstream process/data work and downstream acceptance evidence.
